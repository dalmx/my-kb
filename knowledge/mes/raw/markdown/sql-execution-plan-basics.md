# SQL Server 执行计划入门解读

> 拿到一条执行计划先看三件事：数据流从右往左怎么走、关键算子是谁在干活、估算行数和实际行数差多少——读得懂图，"慢 SQL"就能翻译成"缺索引、统计信息过期还是参数嗅探"。

## 一、定位：本文与《性能排查手册》的分工

- **手册管流程，本文管读图**。《SQL Server 性能排查与优化操作手册》（`sql-server-performance-troubleshooting.md`）讲的是从"卡顿/接口变慢"出发**如何定位慢 SQL、如何处置**；知识库现有性能文档（覆盖索引、索引原则、隐式转换等）都引用了"看执行计划 / Key Lookup / 估算行数"，但**没有一篇教怎么读计划**——本文补这个共同前置技能。
- **分工边界**：Key Lookup 怎么消除（覆盖索引 INCLUDE）手册已详述，本文只讲"在计划里怎么认出它"；统计信息怎么维护见手册索引原则，本文只讲"行数偏差意味着什么"。
- **验证边界**：本知识库不连库。本文所有读图结论是 SQL Server 官方文档层面的通用知识；落到具体项目库的版本与真实表结构，需要 DBA/开发按第五章入口连库自行验证。

## 二、图形执行计划怎么读

### 2.1 数据流：从右往左

- **最右边**是数据源算子（真正访问表/索引的地方），**最左边**是把结果返回给客户端的算子。数据沿箭头从右向左流动，处理顺序也是从右往左读。
- **多分支输入看上下**：Nested Loops 的**上方输入是外层（驱动表）、下方是内层（被探测）**；Hash Match 的**上方是 build（建哈希表）、下方是 probe（探测）**。判断"谁驱动谁"是看计划的第一要务——驱动表行数错了，后面全错。

### 2.2 箭头粗细 = 行数（和行宽）

- 悬停在箭头上可看到 **Estimated Number of Rows（估算行数）**；实际执行计划里还有 **Actual Number of Rows（实际行数）**。箭头粗细表示相对的行数与行大小。
- **粗变细**是正常过滤（WHERE 把数据筛少了）；**细变粗要警惕**——行数越流越多，常见于 Join 扩张（一对多连接无过滤）或中间结果被放大。
- 实际计划中：**估算箭头 vs 实际箭头的落差本身就是诊断线索**（详见第四章）。

### 2.3 开销百分比：只做"同计划内"比较

- 每个算子标注的百分比是其 **Estimated Operator Cost 占整个计划成本的比例**。先打百分比最高的算子，通常就是主要瓶颈。
- 两个注意：
  - 百分比是**优化器估算的相对成本，不是真实毫秒耗时**，也**不能跨计划比较**（A 语句的 90% 不一定比 B 语句的 30% 慢）；
  - 当估算行数失真时，"最贵的算子"可能不是真正拖慢的算子——先核对第四章的行数偏差，再相信百分比。

### 2.4 警告图标与绿色文字

- **黄色感叹号 = 计划警告**，悬停看 Warning 属性，常见三类：
  - **SpillToTempDb / 已溢出到 tempdb**：Sort/Hash 的内存授予不够，数据落到 tempdb 磁盘，开销陡增；
  - **隐式转换警告**（`Type conversion in expression ... may affect "SeekPlan"`）：见第六章实例三；
  - **缺失连接谓词**（Missing Join Predicate）：笛卡尔积风险，几乎必是问题。
- **计划顶部绿色文字 = 缺失索引建议（Missing Index）**：直接给出 CREATE INDEX 草案。它只是线索，有明确局限（每组查询最多一条建议、不检查与既有索引的重叠冗余、不考虑写放大），**必须按手册索引原则评估后再上**，不要照抄。

## 三、关键算子速查

| 算子 | 在干什么 | 什么时候正常 | 什么时候危险 |
|---|---|---|---|
| **Table Scan / Clustered Index Scan** | 全表读堆 / 聚集索引 | 小表（几百~几千行）扫一遍无所谓 | 大表 + 高选择性过滤条件却全扫 = 没走到索引 |
| **Index Seek / Clustered Index Seek** | 按 B 树定位，理想路径 | 有 SEEK 谓词、行数与条件选择性匹配 | 悬停检查 Seek Predicates：没吃到过滤条件就成了"假 Seek" |
| **Key Lookup** | 非聚集索引找到了行，但 SELECT 还要索引里没有的列，**回聚集索引逐行取**（堆表对应 RID Lookup） | 偶发、次数少 | ×执行次数 = 外层行数、开销% 反超 Seek = 缺覆盖索引（处置见手册"覆盖索引与 INCLUDE 列"节） |
| **Sort** | 排序，**阻塞算子**（吃完全部输入才出第一行），需要内存授权 | 行数小 | 内存不够溢出 tempdb（警告图标）；排序大结果集时先想想能不能靠索引顺序免掉 |
| **Hash Match** | 上方输入建哈希表、下方探测；用于 Join 和 DISTINCT/GROUP BY 聚合 | 大表无序数据 Join 的常规选择 | build 侧估算失真 → 内存授予错 → 溢出 tempdb |
| **Stream Aggregate** | 在**有序**输入上聚合（常伴随 Sort 或索引序） | 配合索引序时很高效 | 前面被迫加一个大 Sort 时，成本在 Sort 不在它 |
| **Nested Loops** | 外层每一行去内层索引探测一次 | 外层小 + 内层有索引 = 最快组合 | 外层估算失真（以为 1 行实际 10 万）→ 内层被执行 10 万次 |
| **Merge Join** | 两边输入都有序时归并连接 | 两侧索引序正好匹配 | 为它强行排序时，成本前移到 Sort |
| **Spool（Eager/Lazy、Table Spool 等）** | 把中间行集缓存到 tempdb 工作表；Eager 一次吃完，Lazy 按需吐 | 小规模、UPDATE 的内部保护机制属正常 | 大 Spool = tempdb 压力 + 重复读写；常见于 OR 分支、ROW_NUMBER 更新式写法 |

**记忆钩子**：Seek 好；Scan 看表大小；Lookup 看次数；Sort/Hash 看内存（溢出即警告）；Spool 看规模；Nested Loops 看外层行数估算准不准。

## 四、估算行数 vs 实际行数：偏差意味着什么

### 4.1 在哪里看

- **实际执行计划**（Ctrl+M）选中算子 → 属性窗口对照 **Estimated Number of Rows** 与 **Actual Number of Rows**；箭头悬停也能看。
- `SET STATISTICS PROFILE` 的第二个结果集同时给出 EstimateRows 与实际 Rows（见第五章）。
- 预估执行计划（Ctrl+L）**没有实际行数**——它不执行语句，只有估算。

### 4.2 优化器为什么"命悬估算"

基数估计（CE）完全依赖**统计信息**（直方图，可用 `DBCC SHOW_STATISTICS` 查看）。估算行数一旦失真，连锁反应是：Join 方式选错（该 Hash 选了 Nested Loops）、内存授予错（溢出 tempdb）、索引选错（该 Seek 走了 Scan）。**先查偏差，再谈其他优化**。

> 经验阈值：估算与实际偏差 **10 倍以上**值得作为主嫌疑排查。这是通用经验值，非官方标准，供入门参考。

### 4.3 偏差三大根因

1. **统计信息过期**：大表的自动更新阈值高（旧版本为"500 + 20% 行数"，SQL Server 2016 起兼容级别 ≥130 改用动态阈值），增删改不到阈值就不自动更新 → 估算停在旧直方图上。处置见手册索引原则：**重建索引会自动更新统计信息，重组不会，需单独 UPDATE STATISTICS**，大表建议纳入维护计划定期全量更新。
2. **参数嗅探（Parameter Sniffing）**：存储过程/参数化语句的计划按**第一次编译时的参数值**生成并缓存复用；数据分布倾斜时（同一字段 90% 是同一个值），对个别参数值是灾难。典型表现：**同一段代码时快时慢，慢的时段重启或换个参数就好**。
3. **固定估算的构造**：**表变量**编译时一般按 1 行估算——先灌入大批数据再参与 Join 会严重低估（大批量中间结果应改用 `#` 临时表，手册语句优化原则亦倾向临时表）；多语句表值函数在旧版本同样按固定行数估算（新版本有改进，版本差异待核实）。

## 五、查看入口

### 5.1 SSMS 图形化（日常首选）

```sql
-- 预估执行计划：Ctrl+L（工具栏"显示估计的执行计划"）
--   不执行语句，按当前统计信息画图，适合先看个大概、语句很重不敢跑时
-- 实际执行计划：Ctrl+M（"包括实际的执行计划"），然后照常执行语句
--   真跑并收集：实际行数、实际耗时、警告、溢出信息——诊断一律优先用这个
```

### 5.2 SET STATISTICS PROFILE（无图形界面/程序内）

```sql
SET STATISTICS PROFILE ON;
SELECT GREEN_TYRE_NO, MATERIAL_CODE
FROM BPM_PRODUCTION
WHERE GREEN_TYRE_NO = @no;
SET STATISTICS PROFILE OFF;
```

第二个结果集逐行给出计划：关键列 `StmtText`（算子树文本）、`EstimateRows`（估算）、`Rows`（实际）、`Executes`（执行次数）。适合远程工具/只有查询窗口时用；注意它会**真实执行**语句并收集计数，对高频大查询本身有开销，生产慎用。需要存档对比时用 `SET STATISTICS XML` 取 XML 版计划。

### 5.3 缓存里的计划（没重跑也能看）

`sys.dm_exec_query_stats` + `sys.dm_exec_query_plan` 可以取出计划缓存中已编译的计划（**只有估算值**，无实际行数），配合定位"线上正在慢但没有图形环境"的场景；定位正在执行的语句本身见《SQL Server 查询正在执行的语句 + 阻塞/死锁排查》（`sql-running-queries-and-deadlock.md`）。

### 5.4 计划内绿色 Missing Index 提示

如 2.4 所述：是优化器附赠的索引建议，**只作线索**——它不检查与既有索引的重叠、每组查询最多一条、不考虑写放大与 INCLUDE 覆盖性，按手册索引原则人工评估后再建。

## 六、MES 实战：看到什么 → 诊断什么

以下实例的表名/列名仅作示意（其中 6.1 沿用手册覆盖索引一节的 BPM_PRODUCTION 示例，实际以项目库为准）；确认结论需按第五章入口连库取实际计划验证。

### 6.1 Key Lookup 开销反超 Seek，执行次数 = 外层行数

| | |
|---|---|
| **看到** | Index Seek 上方悬着 **Key Lookup**，Key Lookup 的开销% 比 Seek 还高，其 ×执行次数等于 Nested Loops 外层行数；语句整体慢 |
| **诊断** | 非聚集索引没有覆盖 SELECT 的列，**每命中一行就回聚集索引取一次**；外层行数越多，回表放大越狠。MES 里典型的触发场景：条码/批次单号的单条或小范围查询页面，索引只建在查询列上，SELECT 却带出一堆展示列 |
| **处置** | 按手册"覆盖索引与 INCLUDE 列"节把只查不过滤的列放进 INCLUDE 消除回表（`CREATE NONCLUSTERED INDEX ... INCLUDE (...)`），并评估写放大 |

### 6.2 估算 1 行，实际 10 万行

| | |
|---|---|
| **看到** | 某算子 Estimated 1 / Actual 100000+，常伴随：该走 Hash Match 的地方选了 Nested Loops、Sort/Hash 内存授予严重不足并溢出 tempdb（警告图标）；报表偶发超时且时快时慢 |
| **诊断**（按嫌疑排序） | ① 中间结果装在**表变量/多语句 TVF** 里（固定按 1 行估算）；② **统计信息过期**（对照该表统计信息的更新时间与大表阈值）；③ **参数嗅探**——同一语句不同参数值表现差异大 |
| **处置** | 大批量中间结果改 `#` 临时表；`UPDATE STATISTICS`（或维护计划重建索引）；确认嗅探时对问题语句加 `OPTION (RECOMPILE)` 或 `OPTIMIZE FOR`（此两项为官方支持的通用手段，项目 iBATIS/存储过程内尚未实证，上线前需评估编译开销） |

### 6.3 黄色警告 + CONVERT_IMPLICIT + Scan 顶替 Seek

| | |
|---|---|
| **看到** | 算子带警告 `Type conversion in expression ... may affect "SeekPlan"`；计划里出现 **CONVERT_IMPLICIT** 包住**列**一侧；明明是高选择性的单号/条码条件却走了 Index Scan / Table Scan |
| **诊断** | 过滤条件的**参数类型与列类型不一致**，SQL Server 在比较前隐式转换；当转换落在列一侧，索引通常无法直接 Seek，退化为扫描。MES 高发形态：**varchar 列 + C# 默认传 nvarchar 参数**；以及 `ISNULL` 返回类型陷阱（见《SQL Server 删除重复数据 + ISNULL 类型转换陷阱》，`sql-delete-duplicate-and-isnull-pitfall.md`） |
| **处置** | 让类型对齐：参数按列类型传（或显式 CONVERT 放在**参数/字面量一侧**，绝不包列）；改后重看计划——警告消失、恢复 Seek |
